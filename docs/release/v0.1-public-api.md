# Axrail v0.1 Public Package and API Surface

Status: **approved, implemented, and published for `0.1.0-rc.1`; post-RC development on `main` may contain additional pre-stable APIs that are not part of the published RC1 artifact**.

This document defines the supported v0.1 package/API boundary after architecture gates #19/#20/#21 and explicit approval of `D-v01-public-api-surface`.

The published npm `0.1.0-rc.1` artifacts correspond to source commit:

```text
e4758656c20f6cb90b05eb3429c79010667a2f7d
```

Later commits on `main` do not retroactively change that published API surface.

## Runtime support

Public v0.1 packages target **Node.js 20 or newer** and are **ESM-only**. Package exports provide ESM `import` entry points; CommonJS `require()` compatibility is not part of the supported v0.1 surface.

## Principles

1. `@axrail/harness` is the primary application embedding surface.
2. `@axrail/adapter-sdk` is the primary external engineering-system integration surface.
3. RFC-backed protocol/runtime primitives remain separately importable for advanced integrations.
4. Domain SDKs such as HMI remain above the generic Adapter SDK and are never kernel dependencies.
5. Internal implementation helpers are not public merely because they exist in the repository or emitted `dist/` tree.
6. `@axrail/core` is not a supported public v0.1 package; it remains private/experimental while RFC-0004 and the working Harness composition model are unconverged.
7. Public v0.1 APIs are pre-stable. Public does not mean v1-frozen.

## Not in the supported v0.1 package set

### `@axrail/core`

`@axrail/core` remains private/experimental for v0.1. The supported runtime composition path is:

```text
@axrail/harness
    ↓
AdapterHost
    ↓
Tools / Artifacts / Policy / Approval / Validation / Transactions / Events
```

Applications and third-party Adapters should not depend on `@axrail/core` as compatibility evidence for v0.1.

## Package-level API intent

### `@axrail/harness`

The published `0.1.0-rc.1` intent includes `HarnessRuntime`, `HarnessAgent`, Harness runtime/transaction options, and `AuditFailurePolicy`. This is the recommended application entry point.

Post-RC development on `main` now also contains an experimental `HarnessRuntime.executeChangeSet()` high-level Transactional Mutation path. It requires an explicit provider-bound `TransactionExecutor`: the executor carries `providerId`, Harness requires that provider to be mounted, derives Adapter Policy/Validation scope from the same provider identity, and rejects declared ChangeSet Artifact providers that conflict with it. This prevents governance from being evaluated for one Adapter while an executor performs effects for another. This API was added after the RC1 provenance commit and **is not present in the published `0.1.0-rc.1` package**. It is being validated for a subsequent release under RFC-0009 and must not be treated as retroactively supported RC1 API.

### `@axrail/adapter-sdk`

The package root remains the compatibility entry point for v0.1 Adapter contracts/capabilities and currently re-exports advanced Host utilities for RC compatibility.

Advanced composition utilities also have explicit experimental subpaths:

```text
@axrail/adapter-sdk/host
@axrail/adapter-sdk/registry
@axrail/adapter-sdk/context-registry
```

These subpaths make the intended layering visible without forcing a breaking root-export removal immediately before RC publication. Applications should prefer `@axrail/harness`; Adapter authors should prefer the root contracts; custom runtime/composition authors may opt into the experimental subpaths.

Supported intent includes `AxrailAdapter`, `CapabilityManifest`, `CapabilitySupport`, lifecycle/context contracts, provider-aware `AdapterHost`, and explicit scoped context retrieval.

`approvals()` and `transactions()` remain **experimental v0.1 Adapter surfaces** because the Harness does not yet provide a complete multi-provider orchestration model for them.

Adapter context retrieval is explicit and scoped; sensitive fragments are excluded by default and are never automatically injected into a model prompt.

### `@axrail/tools`

Supported intent includes Tool contracts, `ToolInvocationEnvelope`, provider-aware `ToolRegistry`, `ToolRuntime`, and Policy/Approval runtime contracts. Semantic Tool identity is separate from provider identity; unresolved ambiguity fails closed. Timeout and postcondition errors distinguish known failure from side-effect uncertainty so callers do not treat uncertain outcomes as safe retries.

### `@axrail/artifacts`

Supported intent includes Artifact/ref/snapshot types, `ArtifactProvider`, and `ArtifactProviderRegistry`.

### `@axrail/changesets`

Supported intent includes ChangeSet operation/risk/precondition data contracts, canonical digest helpers, immutable snapshot helper, and inspection helpers. ChangeSets handed to a Transaction are execution evidence and must not be mutated by callers.

### `@axrail/transactions`

Supported intent includes transaction state/mode/context/record contracts, `TransactionRuntime`, `TransactionHandle`, executor/policy/approval contracts and standard bridges. L4/L5 governance floors cannot be bypassed by development escape hatches. Lifecycle observers are observational; authoritative fail-closed audit is expressed through explicit checkpoints.

### `@axrail/policy`

Supported intent includes `PolicyInput`, `PolicyDecision`, obligations, providers, and `PolicyEngine`. Unknown obligations fail closed at governed runtime boundaries. Adapter-owned Policies are Host-scoped to their Adapter identity.

### `@axrail/approval`

Supported intent includes approval request/decision/principal/requirement/evidence contracts, `ApprovalProvider`, `ApprovalService`, `ApprovalError`, local callback helper, and `isApprovalGranted`. Quorum and evidence digest rules are execution semantics.

### `@axrail/validation`

Supported intent includes Validator/context/issue/result contracts and provider-aware `ValidationPipeline`. Adapter validators are host-scoped by provider.

### `@axrail/events`

Supported intent includes Event/EventStore/query/session contracts, in-memory and JSONL stores, `SessionService`, and replay/query helpers. `JsonlEventStore` is an embedded reference provider, not a multi-process/fsync/rotation/retention-grade production audit database. Session replay is not exact model-conversation resume.

### `@axrail/agent`

Supported intent includes model request/response/provider contracts, Agent message/tool/run contracts, `AgentLoop`, and `AgentSession`. `AgentSession` conversation state is process-local in v0.1. Ordinary AgentLoop lifecycle observers are observational by default; authoritative integrations may explicitly opt into event-failure propagation.

### `@axrail/mcp`

Supported intent includes MCP Tool/client/bridge contracts, naming/risk helpers and official SDK client transports. Descriptor fingerprinting is intentionally internal and not exported from the package root.

### `@axrail/model-openai-compatible`

Supported intent is the package-root OpenAI-compatible Responses provider/configuration. Provider transport details must not leak into `@axrail/agent`.

### `@axrail/hmi-adapter-kit`

Supported intent includes canonical HMI capability names, HMI Artifact helpers, manifest helpers, vendor-neutral Tool contracts/factory and risk defaults. It is a domain SDK, not a Harness dependency.

### `@axrail/cli`

Supported intent is read-only diagnostics/inspection plus `runCli()` for embedding/testing. The CLI must not become a privileged side-effect bypass around Harness governance.

## Compatibility expectations

### TypeScript/JavaScript API

v0.1 is pre-stable:

- patch releases SHOULD avoid intentional breaks to documented supported entry points;
- future `0.x` minor releases MAY evolve APIs with release notes/migration guidance;
- experimental surfaces may evolve more aggressively.

### Serialized protocol data

Serialized protocol versions such as `ChangeSet.protocolVersion`, Event `version`, and Adapter protocol metadata are independent from npm package version. Consumers should validate protocol versions explicitly.

### Unknown fields and forward evolution

Consumers of serialized protocol data should tolerate unknown additive fields where safe, while runtimes may explicitly reject unsupported protocol versions or semantics.

## Package/export rules

- public consumers import documented package roots or documented exported subpaths, never `src/...`;
- package exports are intentional entry points;
- internal helpers may physically exist under `dist/` but remain inaccessible through package `exports`;
- public package tarballs include built artifacts, package metadata and Apache-2.0 LICENSE text;
- v0.1 build artifacts intentionally omit source/declaration map files unless source packaging is revisited later;
- `@axrail/core` remains outside the public package graph.

The v0.1 package surface is approved and `0.1.0-rc.1` is public on npm with provenance. Remaining RC1 release closeout, including the exact Git tag/GitHub prerelease finalization, is tracked under #18. Post-RC Transactional Mutation work is tracked separately through the architecture RFCs and Cortex development tasks.

## Post-RC Interaction SDK

`@axrail/interaction-sdk` is a **post-RC main** package under active development. It is not part of the published npm `0.1.0-rc.1` artifact sourced from `e4758656c20f6cb90b05eb3429c79010667a2f7d`.

Current main adds a headless interaction core and typed plugin contracts for third-party engineering applications. Consumers evaluating it before the next npm release should use an appropriate source/main integration workflow and treat its API as pre-stable.

This does not retroactively change the RC1 public package set.


### Model Registry/runtime selection on post-RC main

The post-RC `@axrail/interaction-sdk` surface now includes pre-stable model registry and per-turn model selection contracts.

This work keeps `@axrail/agent` as the model-neutral provider protocol and `@axrail/harness` model-agnostic. It is **not** part of the published `0.1.0-rc.1` artifact.

Current main semantics include explicit/default/singleton model resolution, declared capability checks, plugin model registration, and non-secret model provenance. Automatic routing/fallback and credential storage are not part of this surface.

## v0.2 runtime/model-provider baseline

The published npm `0.1.0-rc.1` artifact remains exactly the 15-package, Node >=20 release produced from commit `e4758656c20f6cb90b05eb3429c79010667a2f7d`.

Post-RC/v0.2 development deliberately changes the future runtime baseline:

```text
Node.js >=22.13.0
CI: Node 22 / 24 / 26
```

Post-RC also adds `@axrail/interaction-sdk` and `@axrail/model-ai-sdk`; the release smoke set therefore contains 17 packages during v0.2 development.

`@axrail/model-ai-sdk` uses Vercel AI SDK as provider infrastructure while keeping `AgentModelProvider` as the Axrail boundary. These facts do not retroactively modify the RC1 package set or runtime support statement.
