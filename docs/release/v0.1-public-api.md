# Axrail v0.1 Public Package and API Surface

Status: **proposed public surface; package publication still blocked on #15 build strategy and #18 release/versioning work**.

This document defines the intended v0.1 package/API boundary after the governed-execution architecture gate in #19 passed.

The goal is not to freeze Axrail at v1 semantics. The goal is to ensure that whatever v0.1 publishes is intentional rather than an accidental consequence of the monorepo source layout.

## Principles

1. `@axrail/harness` is the primary application embedding surface.
2. `@axrail/adapter-sdk` is the primary external engineering-system integration surface.
3. RFC-backed protocol/runtime primitives remain separately importable for advanced/custom integrations.
4. Domain SDKs such as HMI remain above the generic Adapter SDK and never become kernel dependencies.
5. Internal implementation helpers are not public merely because they exist under `src/`.
6. `@axrail/core` is not part of the first supported public package set while the RFC-0004 capability/plugin model and the working Harness/AdapterHost model remain unconverged.
7. Every public v0.1 package remains pre-stable. Public does not mean v1-frozen.

## Not in the supported v0.1 package set

### `@axrail/core`

`@axrail/core` remains experimental/internal for v0.1.

The package explores RFC-0004 capability/plugin/scope semantics, but the working product runtime is currently composed through:

```text
@axrail/harness
    ↓
AdapterHost
    ↓
Tools / Artifacts / Policy / Approval / Validation / Transactions / Events
```

The two extension models have not been fully converged. Applications and third-party Adapters should therefore not depend on `@axrail/core` as a supported v0.1 runtime contract.

Track convergence under #20.

## Package-level API intent

### `@axrail/harness`

Supported v0.1 intent:

- `HarnessRuntime`
- `HarnessAgent`
- `HarnessRuntimeOptions`
- `HarnessTransactionRuntimeOptions`
- `AuditFailurePolicy`

This is the recommended application entry point.

### `@axrail/adapter-sdk`

Supported v0.1 intent:

- `AxrailAdapter`
- `CapabilityManifest`
- `CapabilitySupport`
- Adapter lifecycle/context/provider contract types

Experimental/advanced host APIs:

- `AdapterHost`
- `AdapterRegistry`
- `AdapterContextRegistry`

The optional Adapter surfaces `approvals()`, `transactions()`, and `context()` are currently experimental because Harness does not yet orchestrate all of them as fully as Tool/Artifact/Policy/Validation surfaces. Track this under #20.

### `@axrail/tools`

Supported v0.1 intent:

- `ToolDefinition`
- `ToolCall`
- `ToolResult`
- `ToolExecutionContext`
- `ToolInvocationEnvelope`
- `ToolRegistry`
- `ToolRuntime`
- Policy/approval Tool runtime contracts

Semantic Tool identity and provider identity are separate concepts. Unresolved provider ambiguity is a runtime error, not a registration-order choice.

### `@axrail/artifacts`

Supported v0.1 intent:

- Artifact/ref/snapshot types
- `ArtifactProvider`
- `ArtifactProviderRegistry`

### `@axrail/changesets`

Supported v0.1 intent:

- `ChangeSet` and operation/risk/precondition data contracts
- canonicalization/digest helpers
- immutable ChangeSet snapshot helper
- ChangeSet inspection helpers

ChangeSet is an important serialized governance artifact. Consumers should not mutate a ChangeSet after handing it to a Transaction.

### `@axrail/transactions`

Supported v0.1 intent:

- Transaction state/mode/context/record contracts
- `TransactionRuntime`
- `TransactionHandle`
- Transaction executor/policy/approval contracts
- standard Policy/Approval/Validation bridges

Advanced escape hatches such as `allowWithoutPolicy` are intended for controlled embedding/testing and do not bypass the L4/L5 governance floors.

### `@axrail/policy`

Supported v0.1 intent:

- `PolicyInput`
- `PolicyDecision`
- `PolicyObligation`
- `PolicyProvider`
- `PolicyEngine`

Unknown obligations must fail closed at governed runtime boundaries until an enforcement implementation exists.

### `@axrail/approval`

Supported v0.1 intent:

- approval request/decision/principal/requirement/evidence contracts
- `ApprovalProvider`
- `ApprovalService`
- `ApprovalError`
- `CallbackApprovalProvider` as a local/testing integration helper
- `isApprovalGranted`

Quorum/role/count/distinct-principal requirements and evidence digest binding are execution semantics, not advisory metadata.

### `@axrail/validation`

Supported v0.1 intent:

- Validator/context/issue/result contracts
- `ValidationPipeline`

Adapter-level validator scoping remains a P2 host concern tracked by #20.

### `@axrail/events`

Supported v0.1 intent:

- Event/EventStore/query/session contracts
- `InMemoryEventStore`
- `JsonlEventStore`
- `SessionService`
- session replay/query helpers

`JsonlEventStore` is an embedded durable reference provider. It is not a claim of multi-process, fsync/rotation/retention-grade production audit storage.

Session replay reconstructs Axrail session lifecycle/state. It is not exact model conversation resume.

### `@axrail/agent`

Supported v0.1 intent:

- model request/response/provider contracts
- Agent message/tool/run contracts
- `AgentLoop`
- `AgentSession`

`AgentSession` is process-local conversation state. Durable Agent conversation replay is not part of this v0.1 contract.

### `@axrail/mcp`

Supported v0.1 intent:

- MCP Tool/client/bridge contracts
- `McpToolBridge`
- MCP naming helpers
- risk resolver helpers
- official SDK client adapters/transports

Internal implementation detail:

- descriptor fingerprinting used to refresh/reclassify changed remote Tools is intentionally not exported from the package root.

### `@axrail/model-openai-compatible`

Supported v0.1 intent:

- OpenAI-compatible Responses API model provider/configuration exported by the package root.

Provider-specific transport details should not leak into `@axrail/agent`.

### `@axrail/hmi-adapter-kit`

Supported v0.1 intent:

- canonical HMI capability names
- HMI Artifact helpers
- HMI capability-manifest helpers
- vendor-neutral HMI Tool input/handler/contracts
- standard HMI Tool factory/risk defaults

This package is a domain SDK, not a dependency of `@axrail/harness` or generic protocol packages.

### `@axrail/cli`

Supported v0.1 intent:

- read-only diagnostics/inspection CLI
- deterministic `runCli()` embedding/testing entry

The v0.1 CLI must not become a privileged deployment/write bypass around Harness governance.

## Compatibility expectations

### TypeScript/JavaScript API

v0.1 is pre-stable. Until the release/version policy in #18 is finalized:

- patch releases SHOULD avoid intentional breaking changes to documented public entry points;
- minor `0.x` releases MAY evolve public TypeScript APIs with release notes/migration guidance;
- experimental surfaces may change more aggressively and should be clearly documented as such.

### Serialized protocol data

Serialized protocol data is versioned independently of npm package version where a protocol/event version field exists.

Examples include:

- `ChangeSet.protocolVersion`
- Event `version`
- Adapter `protocolVersion`/manifest metadata

Consumers SHOULD validate protocol versions they understand rather than assuming package version equivalence.

Until a protocol is explicitly frozen, cross-minor serialized compatibility is not guaranteed merely because object shapes are structurally similar.

### Unknown fields and forward evolution

Where a format is explicitly documented as serialized protocol data, consumers SHOULD avoid rejecting unknown additive fields unless strict schema validation is a safety requirement. Axrail runtime code may still reject incompatible protocol versions or unsupported semantics explicitly.

## Export hygiene rules

Before #15 changes package manifests for publication:

1. package root `index.ts` exports must be intentional;
2. internal fingerprints, registries/helpers, test utilities, transport internals, and implementation-only functions should not be exported accidentally;
3. experimental symbols that must remain exported for internal workspace use should be documented as experimental until subpath exports/build packaging can isolate them cleanly;
4. public packages should not require consumers to import from `src/...` paths;
5. examples may depend only on intended public package roots wherever practical.
