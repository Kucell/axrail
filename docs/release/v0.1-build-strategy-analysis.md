# Axrail v0.1 Package Build Strategy Analysis

Status: **recommendation only; build-strategy decision remains open**.

This analysis compares the two build strategies recorded in `D-v01-package-build-strategy` against the actual Axrail monorepo.

## Repository facts

The current repository has these relevant characteristics:

- TypeScript target: ES2022.
- Module mode/resolution: `NodeNext`.
- Runtime packages declare `"type": "module"`.
- Package source already uses `.js` import specifiers from TypeScript where NodeNext emit expects them.
- Public-package boundaries are meaningful architecture boundaries: Harness, Adapter SDK, Tool, Artifact, ChangeSet, Transaction, Policy, Approval, Validation, Events, MCP, model provider and HMI SDK are intentionally distinct packages.
- Most packages are libraries rather than applications.
- The MCP package depends on the external `@modelcontextprotocol/client` package and should keep that dependency external rather than bundling it into Axrail.
- The CLI has a normal Node shebang entry and can be emitted as ESM without requiring a single-file executable bundle.
- The release gate requires declaration files and clean consumer imports, not browser bundles.

## Option A — per-package bundler such as tsup

Typical shape:

```text
src/index.ts
   ↓ bundler
 dist/index.js
 dist/index.d.ts
```

### Advantages

- concise configuration for small packages;
- easy minification/single-file output if needed;
- convenient for future standalone CLI/application bundles;
- can generate declarations with the right tooling/configuration.

### Risks for Axrail v0.1

- Axrail package boundaries are part of the product architecture; bundling can obscure those boundaries and accidentally inline dependencies that should remain external;
- declaration bundling across a tightly connected workspace can create additional type-flattening/debugging complexity;
- each package needs careful `external` configuration so `@axrail/*`, MCP SDK and Node built-ins are not folded unexpectedly;
- bundler behavior becomes part of the library ABI/build story even though Axrail currently needs straightforward Node ESM, not application optimization;
- source maps/stack traces and file-level inspection are less direct if output is aggressively bundled.

## Option B — TypeScript project references / native emit

Typical shape:

```text
tsconfig.build.json
package tsconfig references
       ↓ tsc -b
 dist/**/*.js
 dist/**/*.d.ts
 dist/**/*.map (optional)
```

### Advantages for Axrail

- directly matches the existing `NodeNext` source model;
- preserves the package/module structure rather than converting SDKs into bundled artifacts;
- preserves explicit cross-package dependencies as package imports;
- declaration files reflect the real module graph, which is useful for an SDK/protocol ecosystem;
- TypeScript project references can express and validate the workspace dependency order;
- incremental builds become possible without adding another compiler/bundler semantic layer;
- MCP SDK and other external dependencies naturally remain external;
- the CLI can be emitted as a normal executable ESM entry with its shebang preserved;
- easier to inspect packed artifacts and reason about stack traces during the early project phase.

### Costs

- more initial tsconfig/project-reference setup across packages;
- package manifests must be normalized to `dist` exports/types and proper `files`/`bin` entries;
- build ordering/references must stay aligned with the workspace dependency graph;
- no automatic code bundling/minification, which is not currently a v0.1 requirement.

## Recommendation

For Axrail v0.1, prefer **Option B: TypeScript project references / native `tsc -b` emit**.

Recommended principles:

1. Public SDK/runtime packages emit ESM JavaScript and declaration files to `dist/`.
2. Do not bundle `@axrail/*` dependencies into one another.
3. Do not bundle third-party dependencies by default.
4. Root build uses TypeScript project references to order package builds.
5. Package root exports resolve to `dist/index.js` and declarations to `dist/index.d.ts`.
6. Published package contents are restricted with an explicit `files` list.
7. CLI adds a `bin` entry pointing at emitted `dist/bin.js`.
8. Source maps may be emitted for v0.1 debugging, but source TypeScript need not be runtime entry points.
9. `@axrail/core` remains internal/experimental and need not be published merely because it is buildable.

A bundler can still be introduced later for a specific target such as a standalone CLI binary, browser bundle or edge runtime. That should be a target-specific build choice rather than the default compiler for all Axrail library packages.

## Proposed build layout

Example package:

```text
packages/tools/
├── src/
│   ├── index.ts
│   ├── contract.ts
│   └── runtime.ts
├── dist/
│   ├── index.js
│   ├── index.d.ts
│   ├── contract.js
│   ├── contract.d.ts
│   ├── runtime.js
│   └── runtime.d.ts
├── package.json
└── tsconfig.build.json
```

Example publish manifest direction:

```json
{
  "type": "module",
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    }
  },
  "files": ["dist", "README.md", "LICENSE"]
}
```

The exact version/private fields remain blocked on the public-package/version decisions.

## Implementation sequence after approval

If this recommendation is approved:

1. add a base build tsconfig;
2. add per-package build tsconfigs/references for the proposed public package graph;
3. add root `build` / `clean` scripts;
4. emit JS + `.d.ts` to `dist` while keeping existing source tests intact;
5. normalize package exports to built artifacts;
6. add CLI `bin` packaging;
7. add `pnpm pack`/package-content inspection;
8. add clean-consumer tarball install/import smoke tests;
9. run all of the above under Node 20/22/24 release CI;
10. only then consider setting publish candidates `private: false` and applying approved versions.

## Decision boundary

No build files or package manifests should be migrated solely on the basis of this document. `D-v01-package-build-strategy` remains the architecture gate for #15.
