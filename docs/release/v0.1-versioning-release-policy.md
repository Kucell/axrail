# Axrail v0.1 Versioning and Release Policy

Status: **draft / not yet approved for publication automation**.

This document defines the release rules that can be agreed independently of the package build implementation. It does not enable npm publication and does not override the open package-build or public-surface decisions.

## Release principles

1. Releases are produced from CI, never from an unverified local working tree.
2. No registry token, signing secret, API key, or industrial credential is committed to the repository.
3. A Git tag is created only after the release commit passes the supported Node matrix, TypeScript checks, behavioral tests, package build/pack checks, and clean-consumer import tests.
4. npm/package versions and serialized protocol versions are independent concepts.
5. `0.x` APIs are pre-stable; documented supported surfaces receive migration notes when intentionally changed.
6. Experimental/internal surfaces may evolve faster and must not be used as compatibility evidence for supported packages.

## Version candidates

The v0.1 line uses semantic pre-release identifiers for release candidates:

```text
0.1.0-rc.1
0.1.0-rc.2
...
0.1.0
```

Repository tags use the corresponding `v` prefix:

```text
v0.1.0-rc.1
v0.1.0
```

No tag should be created for an artifact that has not passed the complete release gate.

## Package-version model — open decision

Two models remain viable until `D-v01-versioning-release-policy` is approved.

### Option A — lockstep public package versions

All supported public `@axrail/*` packages in one release receive the same version.

Advantages for v0.1:

- simple compatibility communication for a tightly coupled new ecosystem;
- easier release notes and dependency coordination;
- fewer accidental combinations of untested package versions.

Trade-off:

- packages with no code change still receive a new version.

### Option B — independent package versions

Each public package increments only when its own supported surface changes.

Advantages:

- precise package-level change history;
- fewer no-op version bumps.

Trade-off:

- compatibility and release automation become more complex before package boundaries have matured.

The build/release workflow must not assume either model until the decision is resolved.

## CHANGELOG source of truth

The repository root `CHANGELOG.md` is the human-readable release-note source of truth for the v0.1 line.

Rules:

- development changes accumulate under `## [Unreleased]`;
- supported public API changes must include migration impact when relevant;
- architecture-only/internal changes may be summarized without exposing development-agent logs;
- security fixes are described without publishing exploit detail before a coordinated disclosure is appropriate;
- generated package-specific notes may be derived later, but must not contradict the root changelog.

Recommended sections:

```text
Added
Changed
Fixed
Security
Deprecated
Removed
```

## Protocol versions are independent

The following are not inferred from npm/package version:

- `ChangeSet.protocolVersion`;
- runtime Event `version`;
- Adapter manifest/protocol metadata;
- future Axrail wire/protocol versions.

A package release may support more than one serialized protocol version. Consumers must validate protocol versions explicitly.

## Release gate

A release candidate cannot be tagged until all required checks pass.

### Architecture/API gates

- governed-execution P1 architecture review passed (#19);
- architecture P2 findings resolved or explicitly scoped (#20);
- final public package/API surface decision approved (#17 / `D-v01-public-api-surface`);
- package build strategy approved (#15 / `D-v01-package-build-strategy`).

### CI/package gates

- `pnpm install --frozen-lockfile` succeeds;
- Node 20 / 22 / 24 compatibility matrix succeeds;
- TypeScript check succeeds on every supported Node major;
- full behavioral suite succeeds on every supported Node major;
- all proposed publish packages build to installable JavaScript + declarations;
- package contents are inspected before publication;
- packed artifacts install into a clean consumer fixture;
- clean consumer can import primary package roots without TypeScript source paths;
- hello/HMI reference smoke paths required for the release remain deterministic and credential-free.

### Documentation/security gates

- `CHANGELOG.md` has release notes for the candidate;
- README/public API docs match the package artifacts;
- no package accidentally publishes source-only/private development files;
- no secrets are present in package contents, workflow files, examples, or release metadata;
- license/package metadata are present in published artifacts.

## Dry-run release

Before the first registry publication, CI should support a non-publishing release dry run that:

1. builds every proposed public package;
2. produces package tarballs;
3. prints/archives package file manifests;
4. installs the tarballs into a clean temporary consumer project;
5. imports primary package entry points;
6. runs a minimal Harness/Adapter integration smoke test;
7. emits artifacts for human inspection;
8. does **not** create a Git tag, GitHub Release, or npm publication.

Only after dry-run evidence is accepted should a publish job be enabled.

## Publication workflow boundary

The eventual publish workflow should require an explicit version/tag input or approved release commit. It should not publish automatically on every merge to `main`.

Recommended high-level flow:

```text
prepare release commit
        ↓
CI + package smoke matrix
        ↓
release dry run
        ↓
human/maintainer release approval
        ↓
tag vX.Y.Z[-rc.N]
        ↓
GitHub Release
        ↓
registry publish with provenance where supported
```

Exact build commands and package manifest generation remain blocked on #15.

## Rollback and correction

Published package versions are immutable. A bad publication is corrected with a new version; the same version is never overwritten.

For pre-release candidates, use the next RC number. For a released patch-level defect, issue the next patch version under the approved versioning model.

Do not use Git tag rewriting as a release correction mechanism.
