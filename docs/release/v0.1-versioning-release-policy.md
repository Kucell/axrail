# Axrail v0.1 Versioning and Release Policy

Status: **approved for the v0.1 line; `0.1.0-rc.1` is prepared and dry-run verified but not publicly released**.

Decision `D-v01-versioning-release-policy` selected lockstep public-package versions for v0.1. Serialized Axrail protocol versions remain independent from npm package versions.

## Release principles

1. Releases are produced through verified CI/release workflows, never from an unverified local tree.
2. No registry token, signing secret, API key, or industrial credential is committed to the repository.
3. A Git tag is created only after the selected release commit passes supported Node compatibility, TypeScript checks, behavioral tests, package build/pack checks, clean-consumer imports, and artifact inspection.
4. npm/package versions and serialized protocol versions are independent concepts.
5. `0.x` APIs are pre-stable; documented supported surfaces receive release notes/migration guidance when intentionally changed.
6. Experimental/internal surfaces may evolve faster and are not compatibility evidence for supported packages.
7. Public package versions move in lockstep for the v0.1 release line.

## Version sequence

Release candidates use semantic pre-release identifiers:

```text
0.1.0-rc.1
0.1.0-rc.2
...
0.1.0
```

Corresponding repository tags use a `v` prefix:

```text
v0.1.0-rc.1
v0.1.0
```

The current repository/package manifests are prepared as `0.1.0-rc.1`. No tag or registry publication is implied until an explicit release action occurs.

## Lockstep package policy

The 15 supported public `@axrail/*` packages share one release version during the v0.1 line. This keeps a tightly coupled first-release graph easy to reason about and test as one candidate.

`@axrail/core` remains private/experimental and is not part of this public lockstep package set.

Independent package versioning may be reconsidered in a future architecture/release decision after package contracts stabilize.

## Protocol version independence

Package version does not imply serialized protocol compatibility.

Examples of separately versioned data include:

- `ChangeSet.protocolVersion`;
- Event `version`;
- Adapter capability/protocol metadata.

Consumers should validate supported protocol versions explicitly.

## Changelog source of truth

Root `CHANGELOG.md` is the human-readable release-note source of truth. It must distinguish repository/candidate preparation from an actual published/tagged release.

Until a release/tag is created, changes remain under `[Unreleased]` even if package manifests already carry an RC version.

## Release gate

Before creating a release tag, the selected commit must satisfy:

```text
Architecture P1/P2 gates                 ✓
Approved public package/API surface       ✓
Approved reproducible build strategy      ✓
Node 20/22/24 compatibility               ✓
Frozen lockfile                            ✓
tsc -b ESM+d.ts build                     ✓
Behavioral tests                           ✓
Pack/install/import smoke                  ✓
Package LICENSE/metadata inspection        ✓
Release notes/docs aligned                 required
Explicit maintainer release action         required
```

CI #186 established the first complete `0.1.0-rc.1` no-publish package dry run. CI #190/#191/#192 revalidated subsequent release-hardening changes.

## Dry-run workflow

`.github/workflows/release-dry-run.yml` is an explicit `workflow_dispatch` path that:

- validates the requested lockstep version;
- performs frozen install, source check, build and tests;
- packs and clean-installs the public package graph;
- retains verified `.tgz` artifacts for 14 days;
- has only `contents: read` repository permission.

It does **not** create a tag, create a GitHub Release, authenticate to npm, or publish packages.

## Real publication boundary

Public release mechanics remain tracked by #18. Crossing that boundary requires explicit release configuration/action for:

- tag and GitHub Release creation;
- npm authentication through GitHub secrets/environments;
- provenance/signing/attestation where supported;
- final maintainer approval before registry publication.

Published versions/tags are immutable. Corrections use a new version rather than replacing an existing published artifact.
