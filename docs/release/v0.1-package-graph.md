# Axrail v0.1 Package Dependency and Smoke Graph

Status: **decision-ready implementation map; no package publication decision is implied**.

This document maps the proposed v0.1 public package set against the current workspace dependency graph. It is intended to make the package-build implementation mechanical once the public-surface and build-strategy decisions are approved.

`@axrail/core` is intentionally excluded from this graph because it is experimental/internal for the proposed v0.1 public surface.

## Recommended project-reference build layers

If `D-v01-package-build-strategy` approves native TypeScript project references, a deterministic build can use the following layers.

### Layer 0

Build in parallel:

```text
approval
artifacts
events
policy
tools
validation
```

These packages have no workspace runtime dependencies.

### Layer 1

Build after Layer 0:

```text
changesets
agent
mcp
```

### Layer 2

Build after their Layer 0/1 dependencies:

```text
transactions
model-openai-compatible
cli
```

### Layer 3

```text
adapter-sdk
```

### Layer 4

Build in parallel after Adapter SDK is available:

```text
harness
hmi-adapter-kit
```

TypeScript `tsc -b` should derive ordering from project references rather than hard-coded shell sequencing, but these layers are useful for reviewing the reference graph and CI diagnostics.

## Pack and clean-consumer smoke matrix

Every proposed public package should be packed independently and imported through its package root. A smoke fixture must not import `src/...` paths.

| Package | Minimum clean-consumer verification |
| --- | --- |
| `@axrail/approval` | import `ApprovalService`; construct a local provider; verify package types resolve |
| `@axrail/artifacts` | import Artifact contracts/registry; register a minimal provider |
| `@axrail/events` | import `InMemoryEventStore`; append/read one event |
| `@axrail/policy` | import `PolicyEngine`; register/evaluate one rule |
| `@axrail/tools` | import `ToolRuntime`; register/run an L0 Tool |
| `@axrail/validation` | import `ValidationPipeline`; run one validator |
| `@axrail/changesets` | import ChangeSet digest helper; digest a minimal ChangeSet |
| `@axrail/agent` | import `AgentLoop`; run a deterministic no-Tool model step |
| `@axrail/mcp` | import bridge/client contract without starting a real network server; external MCP dependency must resolve normally |
| `@axrail/transactions` | import `TransactionRuntime`; execute a minimal low-risk local transaction |
| `@axrail/model-openai-compatible` | import provider constructor/config without making a network request |
| `@axrail/cli` | execute installed `axrail --help`; import `runCli()` |
| `@axrail/adapter-sdk` | mount/unmount a minimal mock Adapter through `AdapterHost` |
| `@axrail/harness` | construct `HarnessRuntime`; mount a minimal Adapter; execute an L0 Tool |
| `@axrail/hmi-adapter-kit` | create a canonical HMI project ref and one standard Tool definition |

The smoke project should use packed tarballs, not workspace links, so missing runtime dependencies and incorrect package exports are visible.

## Cross-package smoke scenarios

In addition to single-package imports, the release dry run should exercise three cross-package scenarios.

### 1. Harness + Adapter SDK

```text
clean consumer
  ↓
@axrail/harness
  ↓
mock @axrail/adapter-sdk adapter
  ↓
provider-scoped L0 Tool
```

Verifies the primary application integration path.

### 2. Harness + Agent + governed engineering Tool

Use a deterministic model and a mock L2 Tool with Policy + Approval. No external model API key is required.

Verifies that package packing did not weaken the governed runtime path.

### 3. HMI Adapter Kit reference boundary

Create/mount a mock HMI Adapter using only public package roots and the HMI Kit. No private/company HMI code is permitted.

Verifies that the first reference domain remains an optional layer above the generic Adapter SDK.

## Package-content checks

For each tarball the dry run should inspect at least:

- emitted JavaScript exists under the approved `dist` layout;
- declaration files exist;
- package root `exports` targets files present in the tarball;
- `package.json`, README/license metadata are present as required;
- source-workspace-only files are not accidentally published;
- test fixtures, development-agent records, `.github`, local event logs, credentials and secrets are absent;
- workspace dependency specifiers are transformed/resolved into publishable package dependency ranges by the chosen release process;
- Node built-ins and third-party dependencies remain external unless explicitly intended otherwise;
- CLI tarball contains an executable bin target with a valid shebang.

## Version-model interaction

This dependency graph does not require lockstep versioning, but lockstep is currently the recommended v0.1 release model because the graph is tightly coupled and will be tested as one release set.

If independent versions are selected instead, clean-consumer CI must test the exact dependency ranges written into each packed package rather than relying on one monorepo version assumption.

## Release implementation boundary

This graph is descriptive and can be used by either build strategy. It does not approve:

- the proposed public package set;
- TypeScript project-reference build architecture;
- lockstep package versions;
- npm publication.

Those remain explicit development decisions in `Kucell/axrail-agent`.
